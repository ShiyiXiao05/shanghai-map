## 4. 发现清单

级别定义：**P0** = 阻塞发布/可致数据不可恢复损失；**P1** = 高危（安全、可用性、合规）；**P2** = 中危；**P3** = 低危/改进项。
"证据强度"：**实测** = 本次线上或隔离环境实测；**读码** = 源码确认；**待验证** = 需人工/真机确认。

### 4.1 提审阻塞级（P0）及紧随其后的高危项

---

#### F-01｜P0｜小程序请求通道是"单点"，云托管不可用即全盘不可用（待验证）

- **现象**：`miniprogram/utils/api.js:29-48` 只在**配置期**二选一——`CLOUD_ENV_ID` 非空则**所有**请求走 `wx.cloud.callContainer`，**没有任何运行时降级**；只要云托管未部署、服务名不匹配、实例在冷启动中或构建失败，全站请求只报"网络异常：…"，用户无任何可恢复路径。
- **证据强度**：读码（`api.js:29-48`、`app.js:14-20`、`config.js:8-10`）。当前仓库已回填环境 ID（提交 `1c96854`），说明正式通道已被激活，回落通道只剩改代码一条路。
- **额外放大因素（读码 + 平台规则）**：
  1. `BASE_URL` 指向 `https://shanghai-wish-map.onrender.com`（境外域名，无法 ICP 备案）。小程序 `wx.request` 只能请求 mp 后台配置的合法域名，而项目自己的文档明确写着"`request` 合法域名必须 HTTPS + ICP 备案，Render 域名永远无法备案"（`docs/微信云托管迁移方案.md:8`）。因此**回落通道在真机体验版/正式版中大概率根本用不了**，云托管是唯一可行通道。
  2. 冷启动：`container.config.json` `minNum: 0`。官方《微信云托管开发常识》明确：「设置最小副本为 0 时，需要注意**半小时无请求服务将缩容到 0**，再次请求时将重启服务，扩容新的实例」，且"服务从 0 扩容到 1（冷启动）耗时由服务启动速度决定，请尽可能优化服务启动性能"；项目 runbook 也自述首访会报 `SERVICE_NOT_READY`、"再点一次就好"（`docs/微信云托管部署指引.md:99-100`）——**但代码里没有任何"再点一次"的自动重试**（见 `F-06`）。
  3. 官方同时确认了本项目的核心设计前提：「小程序/公众号可使用 CallContainer，无需域名，因此**不需要在 mp 管理后台配置服务器域名**，从而一开始就无需申请域名，也**无需备案**」；但也提示「**默认公网域名性能有限制，仅能支持接口测试使用，请勿用于正式生产环境**，小程序后台也无法配置使用默认公网域名」——runbook 第 5 步用默认公网域名 curl 自检只能算临时验证，不能当作线上依赖。
- **影响**：若云托管侧任何一环没配好，体验版测试与正式发布会在第一次真机打开时"全军覆没"，且报错信息无法定位原因。
- **建议**：
  1. **立即人工核实**（见第 6 节清单第 1、2 条）：云托管服务列表是否存在 `shanghai-map`、最近一次发布是否成功、公网域名 `/api/health` 是否返回 `{"ok":true}`、日志是否有请求到达。
  2. 代码层加**运行时降级与重试**：`callContainer` 失败（`fail` 或 `statusCode` 异常）后按可配置开关回落 `wx.request`；对超出基础库版本的设备做能力探测。
  3. 冷启动场景给用户"正在唤醒服务，请重试"的明确提示 + 一键重试（`F-06`）。
  4. 若坚持单一通道，至少把 `minNum` 设为 1（成本约每月 ¥21，见迁移方案测算），彻底消除冷启动失败。

#### F-02｜P0｜UGC 完全没有内容安全检测（提审阻塞）

- **现象**：全仓检索 `security.msgSecCheck` / `mediaCheckAsync` / `msgSecCheck` **零命中**。而本应用是典型公开 UGC 平台：
  - 用户可发布地点名称/描述/地址/标签、留言（≤280 字）、照片（≤9 张/地点）、昵称；
  - 通过"公开到公共广场"（`server/routes/places.js:202-215`）后内容**对所有用户可见**，公共接口 `GET /api/public/places`（`server/app.js:43-49`）无需邀请码即可读取，`server/store.js:692-720` 明确聚合 `added_by`（昵称）等字段。
- **证据强度**：读码 + 全仓检索（`grep -rn "msgSecCheck|mediaCheckAsync|security\."` 无结果）。
- **影响**：微信对含 UGC 的小程序有明确的内容审核要求，缺失内容安全能力是**提审被拒或被要求整改**的常见原因；上线后一旦出现违规内容，小程序可能被限制功能、下架，账号主体承担连带责任。
- **建议**：
  1. 服务端在**写入前**同步校验文本：地点 `name/description/address/tags`、留言 `body`、昵称 `nickname` 走 `msgSecCheck`（场景值建议 2 评论 / 1 资料 / 3 论坛）；不通过直接 400 并提示。
  2. 照片走 `mediaCheckAsync`（异步回调或轮询），审核中先标记 `pending`，未通过则拒绝展示/删除。
  3. 接入 `access_token` 缓存（`getStableAccessToken`），并对 `MINIPROGRAM_SECRET` 复用已有配置（`server/auth.js` 已具备 AppID/Secret）。
  4. 补充**人工复核后台**（一个只读管理页或 SQL 操作手册）与"先审后发/先发后审"策略说明。

#### F-03｜P0｜无举报 / 投诉 / 内容管理入口（提审阻塞）

- **现象**：8 个小程序页面中没有任何举报、反馈、屏蔽用户、删除他人内容的入口；后端也没有举报表与相关接口（`server/store.js` 建表语句中无 report 相关表）。用户能删除的只有自己地图内的内容（凭邀请码）。
- **证据强度**：读码 + 页面/路由清单核对。
- **影响**：UGC 平台缺少用户举报与处置机制，不符合小程序平台运营规范中对 UGC 内容管理的要求，是提审高风险项；同时也是《网络安全法》/《网络信息内容生态治理规定》下的运营合规缺口。

#### F-50｜P0｜小程序照片上传在云托管通道下必然失败（官方 100 K 请求上限）

- **现象**：小程序端上传**不做任何压缩**，把整张原图转 base64 后**同时**作为 `full` 与 `thumb` 发送（`miniprogram/pages/detail/detail.js:170-180`，`fileToBase64` 见 `:190-199`），客户端只拦截 >3 MB。而官方《微信云托管开发常识》明确写着：

  > **`CallContainer` 请求大小限制 `100K`，请求中不建议包含图片，可通过对象存储处理。**
  > 小程序/公众号中 `CallContainer` 超时时间不得超过 15 s。
  > —— [微信云托管开发常识](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/guide/debug/know.html)

  base64 会膨胀约 33%，因此**原图超过约 75 KB 即触达上限**；手机以"压缩"模式拍出的照片普遍在 100 KB–1 MB 区间，等于直接命中。
- **证据强度**：官方文档 + 读码（确定）；真机实测待补（需拍一张普通照片验证）。
- **三重叠加的失败面**（其中两条已由本次隔离实验实测）：
  1. **云托管网关**：100 K 请求上限 → 请求被网关拒绝（表现为网络失败/`-606001`），用户只看到"网络异常"；
  2. **回落 Render 通道**（`wx.request`，无 100 K 限制）：`full` 与 `thumb` 完全相同 → 服务端配了 CDN 时忽略 `thumb`，但 body = 2 × 1.33 × 原图大小 > `express.json({limit:'3mb'})` → 原图 >约 1.1 MB 时返回 **500「服务器内部错误」**（实测 `UPLOAD-BODY`）；
  3. **未配置 CDN 时**：服务端要求 `thumb ≤ 150 KB`，而客户端传的是同一张原图 → 原图 >约 112 KB 时返回 **400「缩略图异常，请重试」**（实测 `UPLOAD-THUMB`）。
- **结论**：无论走哪条通道、无论服务端是否配置 CDN，**小程序照片上传对普通手机照片均不可用**——而"照片墙 / 回忆时间线 / 分享海报"三块功能都依赖它。
- **影响**：核心功能不可用；提审时若审核员测试上传，存在因"功能不完整/不可用"被驳回的风险。
- **建议**：
  1. 小程序端补齐压缩（网页版 `public/js/photos.js:36-63` 已有 1200 px 长边 + 240 px 缩略图的 canvas 方案，可直接移植），压缩到 100 K 以内再发；
  2. 根治方案是**图片直传对象存储**（微信云托管对象存储 / Cloudinary unsigned upload preset），接口只传 URL——这也是官方推荐做法；
  3. 统一客户端 / 服务端 / 网关三处阈值，消除当前并存的 3 MB、1.5 MB、150 KB、100 K 四个互相矛盾的限制；
  4. 失败时给可操作提示（"图片过大，已自动压缩后重试"），而不是"网络异常"。

#### F-51｜P1｜marker 图标生成无兜底：一旦失败，地图永久无标记且无任何提示

- **现象**：`miniprogram/pages/index/index.js:70` 在 **`onLoad`** 阶段调用 `prepareMarkerIcons()`；该函数用 `createSelectorQuery().select('#icon-factory').fields({node:true})` 取 canvas 节点，回调里**直接使用 `res[0].node`（无判空，`:297`）**。
  - WXML 节点在 `onLoad` 阶段通常尚未完成首次渲染（官方推荐在 `onReady` 中查询节点），`res[0]` 可能为 `null` → 回调内抛 `TypeError`；
  - 异常发生在框架回调中，**不会传播到外层 Promise**：`drawDotIcon` 的 Promise 既无 `reject` 也无超时（`:290-321`），于是 `pending` 永不归零 → `markerIcons` 永不写入 → `renderMarkers` 在 `:325` 直接 `return` → **地图上一个标记都没有**；
  - 即使走到 `canvasToTempFilePath` 的 `fail` 分支，也只是 `resolve('')`（`:317`），`markerIcons['visited']` 变成空串（falsy），`:325` 同样直接返回——**静默失败，无 toast、无兜底图标**。
  - 次要问题：7 个分类图标复用**同一个** canvas 并发绘制（`:277-287`），无串行化，存在互相覆盖/串色的竞态。
- **证据强度**：读码（确定存在"失败即静默无标记"的路径）；"onLoad 中能否拿到节点"属时序竞态，**必须真机确认**。
- **影响**：地图是本产品的主界面，无标记意味着核心可视化失效，且用户与开发者都不会收到任何错误信号。
- **建议**：节点查询移到 `onReady`；`res[0]?.node` 判空；失败时 `reject`/兜底为内置图片图标；加超时（如 3 s 后放弃并记录）；`pending` 用 `Promise.all` 改写并保证 settle。

#### F-05｜P1｜真实邀请码泄露在仓库文档中，而邀请码 = 删除整张地图的权限

#### F-06｜P1｜小程序端无超时、无重试、无自动降级（可用性）

#### F-07｜P1｜鉴权中间件的数据库异常会导致整个 Node 进程退出

- **现象**：`server/auth.js:75` 在中间件里 `await store.getUser(payload.o)`；Express 4 **不会**捕获 async 中间件的 Promise 拒绝 → 未处理的 rejection 在 Node ≥15 默认终止进程。隔离环境注入"`getUser` 抛错"后，子进程以退出码 1 结束（实测：`AUTH-DATABASE-FAILURE`，`childExitCode: 1`）。
- **触发条件**：任何携带**合法签名 token** 的请求遇到数据库抖动（Neon 空闲断连、连接池耗尽、网络闪断）。网页端不带 token 不受影响，小程序端每次请求都带 token。
- **证据强度**：实测（隔离进程复现）。**生产环境尚未观测到**（当日线上运行正常）。
- **影响**：一次瞬时数据库故障 = 服务进程崩溃 + Render/云托管重启（数十秒不可用）；若数据库持续不可用则形成崩溃循环。
- **建议**：① 中间件整体 `try/catch`，DB 异常时对读请求放行为匿名、写请求返回 503；② 升级 Express 5 或引入 `express-async-errors`；③ 全局兜底 `process.on('unhandledRejection')` 记录并告警（至少不要让进程静默退出）。

#### F-08｜P1｜全站零限流：建图、上传、枚举、登录均可任意调用

- **现象**：全仓检索 `rate-limit`/`express-rate-limit` **零命中**（`server/app.js` 中间件只有 `compression` 与 `express.json`）。可被滥用点：

  - 照片上传 3 MiB 请求体（`server/app.js:16`）无频率限制 → 打满 Cloudinary 配额/带宽；
  - `POST /api/auth/login` 无频率限制 → 刷 `jscode2session`。
- **证据强度**：读码。
- **影响**：Neon 免费库 0.5 GB、Cloudinary 免费额度、Render/云托管实例 CPU 均可能被单个脚本耗尽，直接导致正常用户不可用；配合 `F-05` 的权限模型，枚举成功即等于拿到删除权。
- **建议**：引入基于 IP（Render/云托管场景请先 `app.set('trust proxy', 1)`）的限流：全局 60 req/min；写接口 10 req/min；`/api/auth/login` 5 req/min；邀请码校验失败按 IP 累计，超阈值临时封禁；建图接口加惩罚性限流（如 5 个/小时/IP）。

#### F-10｜P1｜身份可伪造：不携带 token 即可冒名署名（设计层）

- **现象**：`server/routes/identity.js:3-10` 的 `identityOr401` 在 `req.user` 为空时**直接采用客户端传入的署名**（`added_by`/`author`/`who`）。因此即使服务端配置了小程序登录，只要**不带 `Authorization` 头**，任何客户端都能以任意昵称写地点、留言、投票。隔离复现：`AUTH-OMISSION` → 创建 201，`added_by = "Impersonated author"`；编辑后署名变为 `"Another fake author"`。
- **另一面**：这是**有意设计**——网页版永远匿名，署名必须由客户端提供（`identity.js:1-2` 注释）。
- **证据强度**：实测（隔离复现）。
- **影响**：公共广场上可以伪造他人署名；投票（`who`）与留言作者不可信。当前为小范围同学使用，风险可控，但正式发布后是明显的信任缺陷。
- **建议**：至少区分"已知会带 token 的客户端"（小程序）与"匿名网页"：小程序请求缺少 token 时返回 401 触发重登；或给网页端引入匿名会话 ID + 服务端签章（首次访问下发 httpOnly cookie）。

#### F-52｜P1｜"登录过期自动重试"会在登录失败时永久丢失 token

- **现象**：`miniprogram/utils/api.js:56-59` 捕获到 `401 + AUTH_EXPIRED` 后调用 `ensureLogin({ force: getAuthToken() === err.authToken })`；`miniprogram/utils/auth.js:25` 在 `force` 时**先执行 `setAuthToken('')` 清空本地 token，再去登录**。若这次登录失败（服务端未配置小程序登录返回 503、云托管冷启动超时、网络抖动），`api.js` 会抛出错误，而**token 已经被清掉且不会再恢复**——本地既无 token 也无重试入口（无登录页、无"重新登录"按钮、无登出/切换账号入口，全仓 `grep logout|clearStorage` 零命中）。
- **证据强度**：读码（确定）。
- **影响**：用户从"静默自动恢复"退化为"永久未登录状态"：读请求会退化为匿名（服务端对 GET 的失效 token 视为匿名），写请求则持续 401/无法署名，用户只能卸载重进或清缓存——恰好是"过期登录恢复"这个提交想解决的问题的反面。
- **建议**：① 先登录成功拿到新 token 再覆盖/清空旧 token（`const next = await login(); setAuthToken(next.token)`）；② `requireIdentity` 失败时给出可点击的"重新登录"入口；③ 提供登出/切换账号能力。
