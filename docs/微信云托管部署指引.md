# 微信云托管部署指引（小程序正式版通道）

> 目标：把 `server/` 打成 Docker 镜像部署到微信云托管，小程序经 `wx.cloud.callContainer` 调用，
> **免域名、免备案、免 SSL 证书**，正式版可直接提交审核。网页版继续走 Render，完全不动；
> 两端共用同一个 Neon 数据库，数据实时一致。
>
> 本文步骤已按官方文档逐页核对（2026-09）：[快速入门·自定义部署](https://developers.weixin.qq.com/minigame/dev/wxcloudrun/src/quickstart/custom/)、
> [服务设置·代码源/流水线](https://developers.weixin.qq.com/minigame/dev/wxcloudrun/src/guide/service/pipeline.html)、
> [环境创建和管理](https://developers.weixin.qq.com/minigame/dev/wxcloudrun/src/guide/env/)、
> [产品计费](https://developers.weixin.qq.com/minigame/dev/wxcloudrun/src/Billing/price.html)、
> [服务常见问题](https://developers.weixin.qq.com/minigame/dev/wxcloudrun/src/guide/service/faq.html)。
> 控制台界面仍在迭代，个别按钮位置若有出入，以控制台实际为准。
>
> 代码侧已全部就绪：根目录 `Dockerfile`（监听 3000，构建上下文 = 仓库根）、
> 小程序 `utils/config.js` 的 `CLOUD_ENV_ID`（留空 = 回落 `wx.request` 直连 Render）。
> **要回填的值只有一个：环境 ID。**

## 架构

```
小程序 ──wx.cloud.callContainer──> 微信云托管（Docker 跑同一份 Express）──┐
网页   ──fetch──────────────────> Render（不变）──────────────────────┤──> 同一个 Neon / Cloudinary
```

- 走微信官方通道，不进入 `request` 合法域名的备案校验体系，mp 后台**无需配置任何服务器域名**
- callContainer 需基础库 ≥ 2.13.1（本项目 libVersion 3.5.0+，满足）
- 照片缩略图与原图预览直接走 Cloudinary CDN；官方计费文档明确「只通过 callContainer 访问服务不产生流量用量」

## 第 1 步：开通环境（约 5 分钟）

1. 打开 https://cloud.weixin.qq.com ，**小程序管理员微信扫码**登录
2. 进入控制台前选择「小程序/公众号」→ 选我们的小程序；所选主体尚无云托管环境时，会进入创建/无门槛部署流程
3. 创建环境：填**环境名称**（默认 `prod`），系统会在名称后追加一串字符生成**环境 ID**。
   环境会自带一个**同名服务**（名称不可改）——不用它，下一步单独新建 `shanghai-map`
4. 记费与限额（官方计费文档）：**按量付费**、每日结算次日扣费；**仅第一个环境**赠 3 个月免费额度
   （CPU 720 核·时 + 内存 1440 GB·时），一个小程序最多 3 个环境——**别建多余环境**；
   欠费环境会冻结、超 7 天删除且无法恢复
5. 环境 ID 查看位置：控制台**右上角悬浮「环境」TAB**（切换环境的下拉处）

## 第 2 步：新建服务（约 2 分钟）

1. 控制台 → **服务列表 → 右上角【新建服务】**
2. 服务名填 **`shanghai-map`**（必须与 `miniprogram/utils/config.js` 的 `CLOUD_SERVICE_NAME` 一致）
3. 开启**「允许公网访问」**（官方对单一面向用户的服务建议开启；开启后可用公网域名 curl 验证，不影响计费）
4. 创建后点击服务名进入服务详情

## 第 3 步：绑定 GitHub 首次部署（约 5 分钟 + 构建等待）

1. 服务详情 → **「部署发布」** → 选择方式 **「绑定 Github 仓库」**（首次会跳转 GitHub 授权；官方支持 GitHub / GitLab / Gitee，私有仓库也可）
2. 按流水线配置项填写：
   - 代码仓库：`ShiyiXiao05/shanghai-map`，分支 `main`
   - 目标目录：仓库根目录
   - **端口：`3000`**（必须与容器实际监听一致，见下方「端口」说明）
   - Dockerfile 路径：`/Dockerfile`（仓库根目录）
   - 勾选**「推送触发」**：以后 push 到 main 自动构建并发布（官方会在仓库侧建 webhook，别删）
3. **高级配置**里调低规格：CPU **0.25 核** / 内存 **0.5GB**（默认 0.5 核/1G，不调低白花钱）；
   实例副本数最小 **0**、最大 1–2
4. 点「发布」→ 生成发布单（构建 → 部署 → 流量配置三段）。构建+部署约 3 分钟；
   **灰度比例拉到 100% 后点「结单」**，版本才正式全量生效
5. 两个官方文档明确的坑，提前处理：
   - ⚠️ **「开放接口服务」开关：关掉它，并重新部署一次使配置生效**。该开关默认开启，会把容器内对
     `api.weixin.qq.com` 开放接口（含 `sns/jscode2session`）的调用转入云调用通道，可能超时/502——
     我们的登录是自己拿 AppSecret 直调 jscode2session，不走云调用
   - ⚠️ **不要用「手动上传代码包」**：本地代码包限制 **2MiB**，本仓库（含 public/ 静态页）超限，走代码库或 CLI

**端口说明**：业务进程实际监听端口必须与发布时填写的端口一致，否则「日志正常但系统判定部署失败」。
本项目 Express 监听 `process.env.PORT || 3000`（Dockerfile `EXPOSE 3000`），所以填 3000 即可。

## 第 4 步：配置环境变量（约 3 分钟）

服务详情 → **「服务设置」→ 环境变量**，逐个添加（值从本地 `.env` 或 Render 控制台抄，两边保持一致）：

| 变量 | 必填 | 说明 |
|---|---|---|
| `NODE_ENV` | ✅ | `production` |
| `DATABASE_URL` | ✅ | Neon 连接串，与 Render 相同（两端共用一份数据） |
| `CLOUDINARY_URL` | ✅ | 图床，与 Render 相同（不配照片会存进 Neon） |
| `VAPID_PUBLIC_KEY` | 建议 | Web Push 公钥，**与 Render 相同**；小程序写入也要广播推送 |
| `VAPID_PRIVATE_KEY` | 建议 | 同上 |
| `VAPID_SUBJECT` | 可选 | 如 `mailto:admin@example.com`，不配有默认值 |
| `AMAP_KEY` / `AMAP_SECURITY_CODE` | 可选 | 与 Render 相同（`/api/map-config` 用；小程序端不用，配上保持行为一致） |
| `MINIPROGRAM_APPID` | 建议 | 登录署名：mp 后台 → 开发管理 → 开发设置；Render 上已配好，抄同值 |
| `MINIPROGRAM_SECRET` | 建议 | 同上；不配则登录停用、写接口退回客户端昵称 |
| `AUTH_SECRET` | 建议 | token HMAC 密钥，**必须与 Render 侧一致**（同一密钥双后端互验 token） |

- 敏感值只存控制台，不进仓库（`.dockerignore` 与 `.gitignore` 都已排除 `.env*`）
- 官方明确：**构建/部署阶段读不到环境变量**（我们的 Dockerfile 不依赖运行时变量，无影响）
- 官方未明确环境变量是服务级还是版本级——每次发布新版本后到「服务设置」核一眼是否还在

## 第 5 步：验证（我来做联调，你先做两件事）

1. **服务自检**：服务详情「线上版本」有公网域名（形如 `https://xxx.ap-shanghai.run.tcloudbase.com`），
   浏览器或 curl 访问 `/api/health` 应返回 `{"ok":true}`（需第 2 步开了公网访问）
2. 把**环境 ID** 填进 `miniprogram/utils/config.js` 的 `CLOUD_ENV_ID = ''`，开发者工具重新编译
3. 回归清单：冷启动进公共广场 → 加入地图（D3JS39 → 53 地点）→ 加/编/删地点（回收站）→
   打卡、想去 → 传照片与预览（Cloudinary 直链）→ 行程单 → 留言 → **登录署名（重点：验证第 3 步关掉开放接口服务后 jscode2session 正常）**
4. 服务详情「日志」确认请求到达、无报错

> 冷启动表现（官方 FAQ）：实例缩容到 0 后半小时内首访会报 `SERVICE_NOT_READY` / 连接拒绝，
> 控制台显示「服务启动中」，等几秒重试即可——小程序端会提示「网络异常」，再点一次就好。

## 第 6 步：发布正式版（你在 mp 后台操作）

1. 开发者工具「上传」→ mp 后台设为**体验版** → 真机按上面清单回归
2. mp 后台「开发管理 → 服务器域名」：**什么都不用配**
3. 直接「提交审核」（类目建议：工具 > 信息查询，或按首次审核意见调整）
4. 审核通过（通常 1–7 天）→「发布」——正式版入口干净：免扫码、免开调试

## 成本（依据官方计费文档）

- 单价：CPU 0.055 元/(核·时)、内存 0.032 元/(GB·时)，**计费粒度精确到秒**，按实际运行时间计
- **实例缩为 0 后不产生 CPU/内存费用**；callContainer 调用不产生流量用量；公网流量 0.8 元/GB（我们照片走 Cloudinary，不经云托管）
- 0.25 核 / 0.5GB 常驻 ≈ 0.03 元/时 ≈ 21 元/月；缩容到 0 + 每天几十次请求 ≈ **每月几毛钱**
- 首个环境 3 个月免费额度（720 核·时 + 1440 GB·时）足够 0.25 核实例常驻 4 个月——前 3 个月即使常驻也免费
- 按量后付费需账户余额：费用中心充 ¥10 够用一年；**欠费超 7 天环境会被删除**

## 常见问题（官方 FAQ 精选）

- **构建日志空白/超时（>10 分钟）**：基础镜像拉取慢，把 Dockerfile 第一行换成国内镜像源前缀（如 `FROM docker.1ms.run/library/node:20-alpine`）再推
- **日志正常但部署失败**：九成是发布时填的端口与容器实际监听端口不一致
- **登录接口 502/超时**：检查「开放接口服务」开关是否已关闭并重新部署（见第 3 步）
- **概率性 500**：CPU/内存不足或 OOM——0.25 核下 Node + 单请求足够，若出现再调到 0.5 核
- **push 后不自动构建**：查「服务设置 → 流水线」触发开关与分支、GitHub 仓库侧 webhook 是否被误删
- **时区**：容器默认 UTC（与现在 Render 一致，前端展示行为不变）
- **容器无持久化**：扩缩容/重启会清掉容器内文件——本项目全部状态在 Neon/Cloudinary，无影响
